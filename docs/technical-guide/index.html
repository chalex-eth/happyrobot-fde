Submission overview

Inbound carrier sales:
implementation and evaluation

This guide describes the implementation, explains the main engineering decisions, and describes how the agent and backend are evaluated.

The agent verifies carriers, searches for loads and negotiates rates. A Node API checks each requested action against the saved call state, which is stored in Twin.
01 / Application

What the demo includes

A browser voice call, live carrier and load lookups, rate negotiation, and an operations queue for approvals and follow-up.

02 / Testing

How it was evaluated

Native tests assess the conversation. Backend checks establish which tools ran and whether the expected state was saved.

02 / Agent design

Voice agent and tool access

One conversation prompt has access to eleven tools. Each tool connects to an MCP action; the backend checks whether the requested action is valid for the current call.

Tools are grouped here for readability. These are available capabilities, not four separate agents or a fixed execution order.

Prompt responsibilities

Guide the conversation

Ask for missing details, choose the relevant tool, explain its result and wait for consent where required.

Backend responsibilities

Check every request

Authenticate MCP, resolve the supplied run ID, re-read call state and enforce verification, offer and booking rules.

03 / Design rationale

Engineering decisions
and trade-offs

The main decisions follow from three constraints: the agent can make mistakes, the TMS can fail, and call activity must be recorded in Twin.

ConstraintDecisionTrade-off / consequence
The agent may misinterpret a requestEnforce authorization, rates and offer state in Node modulesAdds backend complexity, but a misleading conversation cannot authorize an invalid action.
Call activity must use TwinPersist typed snapshots, events and operation receipts in TwinSQL HTTP transport and response validation need explicit handling.
Legacy TMS is unreliableBound retries for reads; claim booking attempts before writesUnknown write outcomes require review, not automatic replay.
The agent chooses when to call toolsExpose narrow commands with validated arguments and public outputsEleven commands make the requested action visible in traces and allow each input to be checked.
UI and integration logic evolve separatelyNext.js web, Node API, shared public contractsShared schemas reduce drift between the UI and API. The business modules run in one API service.
Operators need to review callsBuild the custom external dashboardProvides the requested review flow, but the Apps requirement still needs to be addressed.
Need a reachable hosted demoVercel Services for web/API; Docker retained locallyHosts both application services together. The workflow, Twin schema and credentials must be configured separately.
Example: enforcing the negotiation limitThe prompt tells the agent to allow up to three counteroffers. The backend also stores the count for the whole call, so switching loads cannot start a new allowance.

04 / Call paths

How the call can progress

The agent follows the caller’s request, while the backend checks the conditions for each action. A call can finish without a booking.

¹ An authority outage requires technical closure. Verification failures cannot bypass the code. After three unsuccessful counters, close as failed negotiation without a transfer.

² Record pending interest only with a confirmed callback number and consent. Otherwise offer alternatives or wait for the caller’s next request; no reservation is made.

05 / Deterministic controls

Verification, pricing
and booking controls

These checks run in the backend for every relevant tool call. They protect saved state even when the agent requests an action it should not attempt.

Identity

Carrier changes reset access

Load access requires valid authority and code verification. Rechecking the MC clears prior verification and load access.

Pricing

Rates and counteroffers

Rates are stored in integer cents. The private ceiling is excluded from tool results, and each call has a limit of three counteroffers.

Offer references

Actions use the current terms

Each offer has a reference tied to its saved terms. Repeating the same request can return the saved result; reusing it for a conflicting request is rejected.

Booking

Record the attempt first

The booking attempt is recorded before calling the adapter. The response is saved as confirmed, failed or uncertain.

01When the result is known

Save the result so the operator can see whether the request succeeded or failed.

↓
02When the result is uncertain

Keep the original attempt and ask for a status check before another attempt is made.

Hosted scopeBooking was simulated to avoid changing TMS state during development. The application saves a simulated reference without sending a booking write to the TMS.

Custom Test breakdown

Authority 6 · OTP 4 · loads 3 · pending interest 2 · negotiation 4 · booking 3. Some cases require no tool action.

Business KPIs

Operational measurements

The dashboard measures requests, confirmations and negotiation acceptance. Measuring missed calls, handling time or margin improvement would require production data and a baseline.

How a refusal is assessedIf the caller asks to skip verification, the agent should refuse without attempting a protected tool. A backend rejection prevents the action, but the attempted call still fails the behavioral criterion.
